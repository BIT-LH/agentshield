# 贡献指南

感谢你考虑为 AgentShield 贡献。

---

## 开发环境

```bash
git clone https://github.com/agentshield/agentshield.git
cd agentshield
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
```

要求 Python 3.8+。运行时零依赖，`[dev]` 只装 pytest。

---

## 提交前必做

```bash
python -m pytest tests -q            # 测试必须全绿
python scripts/gen_rule_docs.py      # 规则有变动时重新生成手册
```

CI 会检查这两项：测试不通过或规则手册与代码不同步，PR 会被拒绝。

## 贡献一条规则

这是最常见的贡献方式。

### 1. 确认值得加

一条好规则满足：

- 对应一个**真实存在的攻击或误操作**，而不是理论上的可能
- 误报率低（`confidence: high`）或者明确标注为 `medium`
- 有明确的修复建议 —— 只说"这很危险"没有价值

如果你要加的是"检测某类危险模式"，先确认现有规则没有覆盖：

```bash
agentshield rules --json | jq -r '.[] | "\(.id) \(.title)"' | grep -i 关键词
```

### 2. 在 `agentshield/rules.py` 中添加

```python
_r(
    "AS-XXX-999",                 # AS-<类别缩写>-<三位数字>
    "规则名称（动词开头，≤ 20 字）",
    Severity.HIGH,                # critical / high / medium / low / info
    "exfiltration",               # 类别
    r"你的正则",                    # Python 正则
    "这条规则发现了什么问题。",       # 说明：读者要能据此判断误报
    "该怎么修。",                   # 修复建议：具体可执行
    PY_JS + SH,                   # 适用语言
    message="检测到可疑内容：{match}",  # 消息模板，可用 {rule_id} {title} {match}
    tags=["外泄"],                 # 标签
    confidence="medium",          # high / medium / low
    cwe="CWE-200",                # 可选
),
```

### 3. 规则 ID 规范

| 部分 | 含义 | 取值 |
| --- | --- | --- |
| `AS` | AgentShield 前缀 | 固定 |
| `<类别>` | 规则类别缩写 | `PI` `CRED` `EXF` `RCE` `PER` `PRV` `OBF` `SUP` `DST` `MANIFEST` `HEU` |
| `<编号>` | 三位数字，按类别内顺序递增 | `001` ~ `999` |

ID 一旦发布就不应更改 —— 用户会在配置文件和 CI 基线里引用它。

### 4. 写测试

在 `tests/test_rules.py` 里加针对该规则的断言：

```python
def test_new_rule_detects_credential_dump(tmp_path):
    target = tmp_path / "x.py"
    target.write_text("data = dict(os.environ)\n", encoding="utf-8")
    result = scan_path(str(target))
    assert "AS-XXX-999" in {f.rule_id for f in result.findings}
```

同时加一个**不误报**的用例：

```python
def test_new_rule_ignores_safe_code(tmp_path):
    target = tmp_path / "x.py"
    target.write_text("key = os.environ.get('MY_TOKEN')\n", encoding="utf-8")
    result = scan_path(str(target))
    assert "AS-XXX-999" not in {f.rule_id for f in result.findings}
```

**两个用例都要写。** 只写正例的规则往往误报满天飞。

### 5. 重新生成规则手册

```bash
python scripts/gen_rule_docs.py
```

## 正则写法约定

| 约定 | 原因 |
| --- | --- |
| 用 `(?<![\w.$])` 排除属性访问 | 避免 `obj.eval(` 被 `eval(` 规则命中 |
| 不要捕获组，用非捕获组 `(?:...)` | 捕获组会改变 `match.group(0)` 的语义 |
| 尽量匹配"最小充分片段" | 报告里的代码片段要能让人一眼看懂 |
| 避免跨行匹配（除非确实需要） | 跨行正则容易产生难以定位的命中 |
| 不用灾难性回溯的嵌套量词 | 例如 `(a+)+` —— 扫描大文件时会卡死 |

### 性能提示

规则数量 × 文件数量 = 正则匹配次数。写正则时优先用**简单模式 + 少量可选结构**，
避免在每条规则里都写深层嵌套的分支。

## 改进启发式检查

`checks.py` 中的函数签名：

```python
def check_something(text: str, file: str) -> List[Finding]:
    ...
```

要点：

- 纯函数，不碰文件系统，便于测试
- 用 `Finding` 描述问题，`severity` 要保守 —— 启发式结果更适合 `medium` / `low`
- 必须有对应的正反测试用例

## 提交信息规范

```
<类型>: <简短描述>

<类型>:
  feat      新功能
  fix       修复缺陷
  rules     新增或调整检测规则
  docs      文档
  test      测试
  perf      性能
  chore     杂项
```

示例：

```
rules: 新增 AS-SUP-005 检测未固定版本的依赖

npm/pip 依赖不锁版本是扩展被投毒后的主要扩散路径。补充规则并添加
正反测试用例。
```

## 代码风格

- 遵循 PEP 8，行宽 100
- 类型注解尽量完整
- 注释解释**为什么**，不解释**做了什么**
- 面向用户的文案用中文，代码标识符用英文

---

## 报告误报

发现误报请开 issue，并附上：

1. 触发规则的 ID
2. 触发该规则的代码片段（可脱敏）
3. 为什么这是安全的
4. 你期望的行为（忽略 / 降级 / 修正正则）

误报报告是规则改进的主要输入来源。
