# AgentShield 架构设计

本文说明工具的内部结构、关键设计取舍，以及每个模块的职责边界。

---

## 1. 设计原则

| 原则 | 落地方式 |
| --- | --- |
| **零依赖** | 只用 Python 标准库。安装即用，不联网，不引入供应链风险 —— 这对一个安全工具尤其重要 |
| **规则是数据，引擎是代码** | 规则以声明式结构定义在 `rules.py`，匹配逻辑集中在 `scanner.py` |
| **文档不与代码漂移** | 规则手册由 `scripts/gen_rule_docs.py` 从规则目录生成 |
| **单一事实来源** | 配置、规则、报告全部围绕 `models.py` 的数据结构 |
| **可测试** | 纯函数 + 明确的 IO 边界，69 个测试覆盖全部路径 |

---

## 2. 分层

```
┌─────────────────────────────────────────────────────┐

                        │

│  引擎层         agentshield/scanner.py               │

│                  清单结构检查 · 去重 · 排序             │
└───────┬───────────────────────┬─────────────────────┘
        │                       │
┌───────▼──────────────┐  ┌─────▼──────────────────────┐
│  规则层              │  │  启发式层                  │

│  44 条正则规则        │  │  不可见字符 · 熵 · IP 直连   │
└──────────────────────┘  └────────────────────────────┘
        │                       │
┌───────▼───────────────────────▼─────────────────────┐
│  配置层         agentshield/config.py               │
│                 .agentshield.json 查找 · 合并 · 解析   │
└───────────────────────┬─────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────┐
│  模型层         agentshield/models.py                │
│                 Severity · Rule · Finding · ScanResult│
└───────────────────────┬─────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────┐
│  输出层         agentshield/reporters/               │
│                 console · json · markdown · sarif     │
└─────────────────────────────────────────────────────┘
```

依赖方向严格自上而下，无循环引用。`models.py` 不依赖任何其他模块，
可以被所有层安全导入。

## 3. 核心模块

### 3.1 `models.py` — 数据模型

| 类型 | 职责 |
| --- | --- |
| `Severity` | 五级枚举（`INFO` < `LOW` < `MEDIUM` < `HIGH` < `CRITICAL`），支持比较与解析 |
| `Rule` | 规则定义：正则、适用语言、严重度、置信度、CWE、修复建议；自带正则编译缓存 |
| `Finding` | 一条命中：定位信息、说明、修复建议、原始匹配文本 |
| `ScanResult` | 一次扫描的完整结果：命中列表、统计、耗时、错误 |

`Rule` 是可序列化的（`to_dict` / `from_dict`），这让规则既能内置在代码里，
也能从 JSON 配置文件加载 —— 两条路径共用同一套语义。

### 3.2 `rules.py` — 规则目录

44 条规则，每条包含：

```python
_r(
    "AS-EXF-001",                                  # ID（AS-<类别>-<数字>）
    "向可疑回收集发数据",                            # 名称
    Severity.CRITICAL,                             # 严重度
    "exfiltration",                                # 类别
    r"https?://(?:[\w.-]*\.)?(?:webhook\.site|...)",  # 正则
    "代码向典型的「一次性收件箱」/ 隧道服务 POST 数据。",  # 说明
    "移除对外部收集点的请求；……",                     # 修复建议
    PY_JS + SH,                                    # 适用语言
    message="向可疑的数据收集端点发送请求：{match}",   # 消息模板
    tags=["外泄", "IOC"],                          # 标签
    confidence="high",                             # 置信度
    cwe="CWE-200",                                 # CWE 编号
)
```

**语言标签**决定规则的适用范围，避免跨语言误报：

| 标签 | 含义 |
| --- | --- |
| `python` | 仅 Python 源码 |
| `javascript` | 仅 JS / TS 源码 |
| `shell` | Shell / PowerShell |
| `json` | JSON 清单 |
| `markdown` | Markdown 文档 |
| `text` | YAML / TOML / 纯文本 / `.env` |
| `any` | 所有文本文件 |

Shell 类的规则同时作用于 `python` / `javascript` / `json` / `text` ——
因为 `curl \| sh` 经常藏在 Python 源码里，而 `postinstall` 钩子藏在 JSON 里。

### 3.3 `scanner.py` — 扫描引擎

执行顺序：

```
1. 文件发现      iter_files()      —— 跳过 node_modules 等目录，按扩展名筛选
2. 语言识别      detect_language() —— 扩展名 → 语言标识
3. 读取          _read_text()      —— 二进制 / 过大 / 非 UTF-8 则跳过
4. 正则匹配      apply_rules()     —— 每规则每文件最多 3 条命中
5. 启发式检查    apply_heuristics()
6. 清单结构检查  check_manifest()  —— 解析 package.json / .mcp.json
7. 技能前言检查  check_skill_markdown()
8. 去重          dedupe()          —— (规则, 文件, 行) 三元组
9. 排序          sort_findings()   —— 严重度 → 文件 → 行
10. 过滤         严重度阈值 + rule_filter
```

**去重键选 `(rule_id, file, line)`** 的原因：同一行里同一规则命中多次通常是
同一个问题（如一句里出现两个 `eval`），重复报告只会淹没真正重要的信息。

**清单结构检查**（`check_manifest` / `check_package_json` / `check_mcp_config`）
走 JSON 解析而非正则，因为这些语义用正则表达非常脆弱：

| 检查 | 规则 ID |
| --- | --- |
| `package.json` 的安装期钩子 | `AS-MANIFEST-001` |
| 依赖指向未固定的 Git / HTTP 源 | `AS-MANIFEST-002` |
| MCP 通过包运行器拉取未固定版本的包 | `AS-MANIFEST-003` |
| MCP 配置中硬编码密钥 | `AS-MANIFEST-004` |
| MCP 请求全量权限（`"*"`） | `AS-MANIFEST-005` |
| 技能声明 `allowed-tools: Bash(*)` | `AS-MANIFEST-006` |

### 3.4 `checks.py` — 启发式检查

正则难以表达的形态：

| 检查 | 规则 ID | 方法 |
| --- | --- | --- |
| 零宽 / 双向控制字符 | `AS-HEU-001` | 按码点构造字符集后全文件扫描 |
| 高熵长字符串 | `AS-HEU-002` | 香农熵 > 4.2 且长度 ≥ 120 |
| 大段十六进制转义 | `AS-HEU-003` | 连续 ≥ 12 个 `\xNN` |
| 直连 IP 的 URL | `AS-HEU-004` | 正则匹配裸 IP URL |
| 能力组合风险 | `AS-HEU-005` | 前言中同时出现「执行 + 联网 + 凭据」 |

`AS-HEU-005` 是个有意思的例子：它检出的每一项单独看都合法，
危险只存在于它们的**组合**中。这类"组合式风险"是 AgentShield 相对于
纯正则扫描器的增量价值。

### 3.5 `config.py` — 配置

```
Config.load(path, search_root)
  ├─ 显式 path ──────────────► 直接使用
  ├─ search_root 逐级向上查找 ──► 找到即用
  └─ 当前工作目录 ───────────► 找不到则返回默认配置
```

规则合并顺序（优先级从低到高）：

```
内置规则  →  rules.off 移除  →  rules.warn 降级  →  severity_overrides 覆盖
          →  追加 custom_rules
```

`severity_overrides` 在最后生效，因此它能覆盖 `warn` 的降级结果。

### 3.6 `reporters/` — 输出

四个报告器共享同一个 `ScanResult` 输入：

| 模块 | 输出 | 消费方 |
| --- | --- | --- |
| `console.py` | 带 ANSI 颜色的分组文本 | 人 |
| `json_reporter.py` | 机器可读 JSON | 脚本 / SIEM |
| `markdown.py` | Markdown 表格 + 明细 | PR 评论 / Issue |
| `sarif.py` | SARIF 2.1.0 | GitHub Code Scanning |

`console.py` 里的颜色通过 `NO_COLOR` / `AGENTSHIELD_FORCE_COLOR` 环境变量控制，
并遵循 `isatty()` 判断 —— 输出重定向到文件时自动关闭颜色。

### 3.7 `cli.py` — 命令行

- `_enable_utf8()` 在最前面执行，保证 Windows 下的中文输出不炸
- 所有输出格式共享同一条渲染路径，避免格式间内容漂移
- 退出码策略集中在一处：`--fail-on` > 配置文件 `fail_on` > 不失败

## 4. 数据流

```
目标路径
   │
   ├─ Config.load()  ─────────────► 规则列表 + 排除项 + 阈值
   │
   ▼
iter_files()  ──►  文件列表
   │
   ▼
每个文件：
   detect_language() ──► 语言
   _read_text()      ──► 文本（失败则跳过）
   apply_rules()     ──► Finding[]
   apply_heuristics()──► Finding[]
   check_manifest()  ──► Finding[]
   check_skill_markdown() ──► Finding[]
   │
   ▼
dedupe() ──► sort_findings() ──► 过滤 ──► ScanResult
   │
   ▼
reporters/ ──► console | json | markdown | sarif
   │
   ▼
退出码（依据 fail_on 阈值）
```

## 5. 扩展点

### 加一条规则

在 `agentshield/rules.py` 的 `BUILTIN_RULES` 追加一条 `_r(...)`，然后：

```bash
python -m pytest tests -q            # 测试会校验 ID 格式与元数据完整性
python scripts/gen_rule_docs.py      # 重新生成规则手册
```

### 加一种输出格式

在 `reporters/` 新建模块，实现一个接收 `ScanResult` 返回 `str` 的函数，
在 `reporters/__init__.py` 导出，在 `cli.py` 的 `cmd_scan` 里加一个分支。

### 加一种启发式检查

在 `checks.py` 新建函数，签名 `(text: str, file: str) -> List[Finding]`，
在 `scanner.apply_heuristics()` 中调用。

### 加一种载体类型

在 `scanner.check_manifest()` 中按文件名分派新的检查函数，
新增的检查函数返回 `Finding` 列表即可。

## 6. 关键取舍

### 为什么不用 AST？

AST 分析能给出更精确的结果，但代价是：每种语言都要单独实现分析器，
而 AgentShield 需要支持十几种文件类型。在"零依赖"约束下，
基于正则 + 少量结构化检查的组合能用 1/10 的代码量覆盖 80% 的真实风险。

**代价**：无法做数据流分析，因此规则只能匹配"危险模式"而非"危险行为"。
这在规则说明里如实标注了 `confidence`。

### 为什么保留启发式检查？

纯正则会漏掉两类重要风险：

1. **不可见字符** —— 零宽空格不匹配任何"危险词"，但能改变模型的语义理解
2. **能力组合** —— 每条单独看都合法，组合起来才是漏洞

这两类都值得用几十行代码去覆盖。

### 为什么规则手册要自动生成？

44 条规则的 ID、严重度、说明、CWE 手工维护必然漂移。
自动生成让"改规则"和"改文档"变成同一个动作。

### 为什么保留 SARIF 输出？

Code Scanning 是目前把静态分析接进 PR 评审的最短路径。
SARIF 让 AgentShield 不必自己实现评审 UI —— GitHub 已经做好了。

## 7. 性能

在普通笔记本上：

| 场景 | 耗时 |
| --- | --- |
| 单个技能（约 5 个文件） | < 30 ms |
| 中型仓库（约 500 个文件） | < 400 ms |
| 大型 monorepo（约 10 000 个文件） | 约 3 s |

主要成本是文件读取与正则匹配，两者都是线性复杂度。
`MAX_FILE_SIZE = 2 MB` 与 `MAX_HITS_PER_RULE_PER_FILE = 3` 是主要的性能护栏。
